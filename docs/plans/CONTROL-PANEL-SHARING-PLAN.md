# Control panel, named memories and peer sharing - plan

Authorization: repository owner (chat, 2026-10-02). Decisions: peers receive READ-ONLY copies published by the owner; the sharing
transport uses an OPTIONAL dependency (`cryptography`, extra `share`) so the core stays dependency-free; first transport is
Wi-Fi/LAN only (no Bluetooth: the standard library supports it only on Linux); do modes 1 and 2 and the control panel together.
Stacked on `feat/learning-harness` (PR #4, not merged). No tag, release, PyPI publication or version bump.

## Mode 1 - named memories on one machine (T18)
`zero-mem memory create|list|use|remove|path`, a registry of name -> data root in the config dir, a global `--memory NAME`
option, and `zero-mem link AGENT --memory NAME` that prints (and optionally applies) the MCP registration bound to that memory.
Many agents can point at one memory; one agent can be pointed at another.

## Control panel (T19)
`zero-mem ui`: local web app, stdlib only, loopback only, session token, Host/Origin/CSRF checks. Input: add, ingest with preview,
proposal inbox (approve/edit/reject/revoke), learn from transcript. Output: search and browse with provenance, brief preview
("what would agent X receive for this task"), status, eval, audit log. Admin: settings, agents and grants.

## Mode 2 - peer sharing over the LAN (T20, then UI in T21)
Threat model and rules (ADR-V170-05, written by T20):
- OFF by default (`[sharing] enabled=false`), requires `pip install "zero-mem[share]"`, honors the kill switch, binds only to a private
  LAN address unless an explicit flag allows otherwise, serves only while `zero-mem share serve` runs, with an expiry.
- Transport: TLS 1.3 with self-signed certificates generated by `cryptography`, authenticated by PINNED fingerprints (no CA, no
  trust-on-first-use without the invite). No home-made cryptography.
- Pairing: the owner creates a one-time invite string `zm1:...` (host, port, server certificate fingerprint, a >=128-bit one-time token,
  expiry, offered scopes). The joiner connects, verifies the pinned fingerprint, presents the token and its own certificate; the owner
  records the joiner's certificate fingerprint as a paired peer. Later connections need mutual TLS with both pins. Tokens are single-use
  and short-lived; every failed attempt is rate limited and audited.
- Authorization: the owner grants each peer read access per space, memory type, project and name prefix, with an expiry; default is
  nothing. Serving reuses the access policy (a peer is a profile). Only active, non-forgotten, non-secret sources are listed; content is
  re-scanned for secrets before it leaves; size and count caps apply.
- Receiving: pull-based. Imported sources land in a quarantine space `ks-peer-<peer id>` with provenance (peer, digest, fetched_at) and
  lifecycle `observed`; they are returned by recall only when the receiver enables it; imported `rule`/`decision`/`gotcha` become local
  PROPOSALS, never active memory (unverified claims must not become active facts). Revoking a grant stops future pulls and sends
  tombstones for forgotten items; copies already pulled cannot be recalled remotely (documented).
- Everything is audited; the panel and CLI show who can read what.
