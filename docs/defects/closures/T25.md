## Fixes
- `src/storage/platform.py`: `lock_wait_seconds()` (default 30 s, env `ZERO_MEM_LOCK_WAIT_SECONDS`, invalid values ignored), `_Backoff` jittered exponential poll 5 ms -> 250 ms (POSIX flock and Windows LockFileEx loops, never sleeps past the deadline), CreateFileW errors carry `.winerror`.
- Canonical-stream lock users use `lock_wait_seconds(...)`: provisioning (append + admin), learning, learner state (10 -> 30 s), workspaces, learning settings (15 -> 30), eval harness (15 -> 30), share invites/identity, jsonl_capture (5 -> 30). `learning_lock` types only a real timeout as "timed out", other lock failures keep `stream_busy` but name the platform code in the message.
- Critical sections reviewed: propose holds `learning.lock` for log refresh + one append only; secret scans/deny patterns run before the lock; no network/hashing of big files/projection under a canonical lock. Not changed.
- `share/server.py`: `stop()` is idempotent AND waits (<= 15 s) for the winning stopper to finish, so `serve_stop` is audited before any `stop()`/`serve_forever()` caller returns. An idle connection never delays stop (connection threads are daemon and not joined; accept loop polls every 0.5 s).
- Fair ticket queue: not added (jitter + long bound was sufficient in stress).

## Honest notes

The macOS failure is therefore not proven to be a 30 s timeout; the likeliest remaining causes (a non-timeout lock error mislabelled `stream_busy`, lockstep starvation) are addressed and will now print their real reason.
- Not verifiable here: Windows (CreateFileW/LockFileEx path, winerror classification) and macOS (flock/fsync timing). The T23 test now injects at `open_regular`, shared by both branches.
