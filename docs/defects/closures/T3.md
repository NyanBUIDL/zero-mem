## DEF-054 - default corpus root (upgrade no longer drops the corpus)

Root cause: no `paths.corpus_root()`; `zero-mem upgrade` only read `ZERO_MEM_CORPUS_ROOT`, so without the env var it
rebuilt a derived DB with 0 corpus units and reported `SUCCESS`/`READY`; backup also only included the corpus when the env
var was set.

Fix (`zero_mem/paths.py`, `commands_setup.py`, `upgrade.py`, `backup.py`, `commands_doctor.py`):
- `paths.corpus_root()`: `ZERO_MEM_CORPUS_ROOT` (must be absolute) else `<data root>/data/corpus`; `corpus_root_is_explicit()`;
  `ensure_corpus_root()` creates the 0700 root, `blobs/` and an empty 0600 `corpus_sources.jsonl` (idempotent, never rewrites a registry).
- setup creates it. upgrade resolves it (an explicit env root must validate; a missing default dir on an older install means "no corpus", not an error).
- upgrade fails BEFORE activation (active DB untouched) with `CORPUS_PROJECTION_EMPTY` when the registry has sources but the rebuild yields 0 units, and with
  `CORPUS_ROOT_UNRESOLVED` when the active DB serves corpus units but the rebuild found none (the exact DEF-054 scenario). The success report gains `corpus: {sources, units}`.
- backup includes the default corpus (existing manifest/verify logic reused: registry + sha256-verified blobs). restore carries the corpus inside the atomic data-root swap
  (`data/corpus`), so a restore of a backup works with no flags; an explicit env root still requires `--corpus-root` (`CORPUS_TARGET_REQUIRED`, unchanged); a live default corpus
  that the backup does not replace is moved into the new data root instead of being deleted with the old one.
- doctor `corpus` check is real: WARN empty / missing, WARN "registry has N source(s) but derived store has 0 corpus units (run zero-mem upgrade)", PASS with counts, FAIL on a
  malformed registry or unsafe root. Non-mutating, no filesystem paths in messages.

## DEF-055 - hyphen / punctuation queries

Root cause: `_FTS_SPECIAL.sub("", token)` deleted `-` and `+`, so `blue-green` became `bluegreen` (0 hits) and `C++` became the prefix `c*`; multi-term
queries masked it through the OR fallback.

Fix (`src/corpus/retrieval.py`, `query_planner.py`): the query is split on every non-word character (letters, digits, combining marks; `_` is a separator, as in the
FTS5 tokenizer) into separately quoted terms: `blue-green` -> `"blue"* "green"*`, `C++` -> `"c"` (single characters are exact, never a prefix). Every term is quoted, so FTS
operators cannot be injected. The hyphenated original is also scored as an adjacency phrase bonus (+1.0). `normalize_query_text` now applies NFC (units are stored NFC).
Vietnamese: with SQLite 3.45.1 `unicode61` folds only the diacritics it knows (for example `Ưu tiên` matches `uu tien`); tone-marked forms such as `ể` are matched by
exact accented queries (case-insensitive, NFC/NFD-insensitive, also inside hyphenated words). The design note's "diacritics fold correctly" holds for exactly these cases;
accent-insensitive search of tone-marked text would need a tokenizer change (`remove_diacritics=2`) in the FTS DDL, which is derived-store scope (T2) and not done here.

## DEF-061 (query side) - limit, ranking, duplicates

Fix (`src/corpus/query_planner.py`, `retrieval.py`):
- `DEFAULT_RESULT_LIMIT = 20` (was 100) in `build_query_plan` / `CorpusQueryPlan`; `MAX_RESULT_LIMIT = 500` is the internal ceiling, so callers (benchmarks, evidence building) can still ask
  for more (`limit=100` is honoured); invalid limits fall back to the default. The candidate-discovery window never shrinks below `_DISCOVERY_CAP_FLOOR = 5000` so a smaller result limit does
  not reduce recall (both knobs are module constants).
- Ranking is BM25 (k1=1.2, b=0.75, unit-length normalization, adjacency phrase bonus) computed in Python over the AUTHORIZED candidates only. SQLite's FTS5 `bm25()` was deliberately NOT
  used: it takes IDF and average length from the whole FTS table, so unauthorized rows would shift authorized scores/order and break the authorization-before-influence invariant that
  `test_hidden_candidate_non_influence` pins. Deterministic ties are unchanged: (-score rounded to 6 decimals, profile, project, source_id, unit_id, unit_order).
- Within-source duplicates (`duplicate_of IS NOT NULL`, same source so same scope) are excluded in the discovery SQL, so they are collapsed and cannot consume the discovery cap; identical
  text in DIFFERENT sources is still returned (authorization identities stay distinct; tested).
- Without FTS5 the fallback path now returns only units that match the query (it used to return every authorized unit with score 0).
