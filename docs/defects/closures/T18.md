# T18 closure - named memories and `link`

Evidence: `tests/unit/test_t18_memories.py` (registry schema/atomic/.bak/corruption, names, create/list/use/remove/rename and
refusals, 16-case precedence matrix, isolation, link for four agents, profile registration, --apply gating, 3x4-process
concurrent create, real stdio MCP server from link args). Full suite: 6599 passed, 14 skipped, 2 failed (the known root-only
test_m9_6_hardening failures). The tests were written after the implementation (not strictly RED-first); on the base commit
they fail at import (`zero_mem.workspaces` absent).

## Proposed defect rows (not added to the registry)
- DEF-120: `config.json` stores absolute data paths and is validated against the CURRENT data root, so one config dir cannot serve
  two data roots: `ZERO_MEM_DATA_ROOT=<other> zero-mem setup/add` fails with "configuration memory path mismatch" once another root
  was set up. Worked around (not fixed) with `ZERO_MEM_CONFIG_PATH` (per-memory config.json in the memory root).
- DEF-121: `ZERO_MEM_CORPUS_ROOT` inherited from the environment silently redirects the corpus of any data root, breaking isolation
  between roots; named memories drop it when selected.
- DEF-122: `hermes-integration.json` and `settings.toml` live in the shared config dir, so they are global, not per memory.
- Note: `paths._reject_symlink` rejects every symlinked ancestor (e.g. macOS `/tmp`), which also applies to `memory create --path`.

## Deferred
`--memory` after the subcommand works for the memory commands, mcp-config/serve and `link`, but for doctor/setup/backup/upgrade/etc.
it must precede the command. No Windows/macOS run was possible here.
