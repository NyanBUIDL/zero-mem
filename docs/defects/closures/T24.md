# T24 - PR #5 automated review (4 findings): evidence and proposed defects

Branch `wt/t24` (base ca83eea). `DEFECT-REGISTRY.md` was NOT edited; rows below are proposals. All four findings reproduced (RED first).

- **DEF-180** (medium, fixed) tombstone cursor lost same-timestamp rows. RED: 5 tombstones with one timestamp, page size 2, client pull applied 2 of 5;
  a tombstone created at the saved cursor's timestamp was never returned. Fix: owner orders by `(forgotten_at, source_id)`; `since` is now an
  inclusive bound, new `after=TS|SOURCE_ID` is strictly-after for paging within a pull; reply adds `next` (parser tolerates its absence from
  older owners). The persisted cursor is the last handled timestamp, re-read and de-duplicated by the import log. Old `since=` still works
  (now inclusive, which is the safe direction). Tests: `tests/unit/test_t24_tombstone_cursor.py`.
- **DEF-181** (medium, fixed) a failed tombstone application (local forget error, proposal not withdrawable) advanced the persisted cursor,
  skipping it forever. RED: injected `_operator_forget` failure, then the retry applied nothing for it. Fix: processing stops at the first
  applicable-but-failed tombstone; the cursor stays at (not past) it; `PullReport.tombstones_failed` lists it; retry applies it exactly once.
- **DEF-182** (medium, fixed) a changed rule/decision/gotcha left the earlier pending proposal reviewable and a tombstone withdrew only the newest.
  RED: v1 and v2 both pending after the second pull; tombstone left v1 pending / revoke for approved v1 not proposed. Fix: the import log keeps
  all proposal ids per (owner, source); a new proposal withdraws earlier pending ones (approved never touched); a tombstone handles every id.
- **DEF-183** (medium, fixed) the panel pull confirmation signed only (source id, digest, action): a pinned-but-untrusted owner could change
  ref / type / kind / size between preview and confirm. RED: with a consistently altered manifest and fetch the confirm imported it. Fix:
  HMAC-SHA256 with a per-session random secret over the canonical JSON of owner id, every row field and the totals, compared with
  `hmac.compare_digest` on a freshly fetched plan. The grant preview had the weaker form of the issue (counts not rechecked): the grant
  confirmation is now bound to peer, spec and the previewed counts/types/references and is refused if they changed. Tests:
  `tests/unit/test_t24_ui_binding.py`; the existing t21 abort test now expects the new message.
