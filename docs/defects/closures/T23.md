## Root cause

Not reproducible on Linux by stress (8 procs x 6 reps, 4 procs x many reps: 0 failures) so the evidence is by reading: dedupe check and append are already inside one critical section (learning.lock) and readers already ignore a torn tail, but `src/storage/platform.py::locked` and `open_regular` converted any non-BlockingIOError OSError (and any open error, e.g. EACCES/EINTR/ENOLCK on macOS) into a non-retried UNAVAILABLE/UNSAFE_PATH, and `append_canonical_event` had no retry around open/fstat/read/fsync. Any single transient error = one `error` result. The real reason was also hidden by the assertion (now printed).

## Fix

- `platform.py`: `is_transient_oserror`, `retry_transient_io` (bounded ~0.5 s), `PlatformStorageError.transient`; lock-file open retried; flock transient errors retried until the lock deadline then typed LOCK_TIMEOUT; real errors still fail fast.
- `provisioning.append_canonical_event`: whole open/check/write/fsync retried only while no byte was written (never re-sent after a write); lock timeout -> `stream_busy`.
- All `locked(` users (learning, learner state, share identity/invites, workspaces, settings, eval harness, registry, jsonl_capture, retrieval db) inherit the lock hardening. Share audit/grants/provisioning events go through `append_canonical_event`. Workspaces/invite/identity/learner/settings already use `retry_transient` for `os.replace` (T13/T17). eval_harness history append fixed here. Not changed: backup/upgrade/paths one-shot replaces (single operator, not racing agents).
