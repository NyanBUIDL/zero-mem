## Current implementation and gap

`src/integration/zero_mem_runtime.py` currently owns only the master boolean and a module-level mutable default. `RegistrationAdapter` accepts an optional store and constructs `_CaptureWriter` locally, while the production path does not establish a single composition root for the canonical writer. This permits adapter-local ownership and leaves lifecycle ownership implicit.

The existing `JsonlCaptureStore` already provides process locking, durable append, and `close()`. `BridgeConfig` already validates the capture root. WP-25 will compose these existing pieces without changing canonical storage.

## Exact scope

1. Add an explicit runtime configuration and health/lifecycle state.
2. Add `ZeroMemRuntime.open(...)`/factory behavior that opens one `JsonlCaptureStore` for a validated root, or accepts an explicitly injected store only as a test seam.
3. Make close deterministic and idempotent; reject appends after close.
4. Retain strict master gate behavior without using it as a writer/path resolver.
5. Update `RegistrationAdapter` to obtain its writer from the runtime and delegate shutdown to the runtime.

## Interfaces

- `RuntimeConfig(capture_root: Path, enabled: bool)` — immutable, validated input.
- `RuntimeHealth(status: Literal["OPEN", "CLOSED"], reason_code: str | None)` — immutable observation.
- `ZeroMemRuntime.open(config, *, store=None) -> ZeroMemRuntime` — only runtime composition entry point.
- `runtime.writer` — the owned `CaptureStore` while open.
- `runtime.health() -> RuntimeHealth`.
- `runtime.close() -> None` — idempotent, bounded.

The existing `configure/get_runtime` master switch compatibility API remains available for M7 tests; it must not open a writer or infer a path.

## Migration/compatibility impact

No database or canonical JSONL migration. Existing callers that inject a store remain supported as an explicit test seam. Existing master-gate tests remain valid. Adapter shutdown remains callable and becomes runtime-backed.

## Security/provenance impact

No new identity or authorization semantics. The runtime owns the configured canonical root and never logs payloads, secrets, or absolute-path details in diagnostics. Canonical provenance remains generated by existing capture mapping and storage code.

## Recovery and rollback

Close only releases the process lock; it never deletes or rewrites canonical data. Rollback is file-local: restore the prior runtime and adapter modules; no data migration is required.
