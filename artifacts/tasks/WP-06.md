## Objective

Ensure injected memory cost is bounded by relevant evidence, avoids stale/duplicate repetition, and is measured against a no-memory baseline.

## Why This Exists

M7 already caps evidence and defaults to NO_MEMORY, but lower retrieval ordering can surface stale items, unchanged evidence may be reinjected across turns, and repository benchmarks do not quantify token savings or repeated injection.

## Current State on master

`memory_router.py` uses deterministic intent routing. `evidence_builder.py` caps primary/supporting evidence and a token estimate. `injection_adapter.py` injects a data envelope on `pre_llm_call`. `hardening.py` validates/sanitizes evidence.

## Evidence

Existing M7 tests verify bounds and no-memory behavior. Audit found no measured baseline for prompt tokens, repeated evidence, avoided calls, or end-to-end cost. Repeated-injection impact is `Needs verification`.

## Problems Found

- PERFORMANCE P2: context quality depends on F-009 chronological retrieval.
- COST P2: no metric for injected tokens or unchanged evidence repetition.
- ARCHITECTURE P2: evidence freshness/derived lag is not represented.
- Semantic duplicate suppression across events is `Needs verification` and must not become a mandatory model feature.

## Affected Components

M7 router/budget/evidence/envelope, M8 metadata/calibration, Hermes/generic context adapters, observability.

## Desired State

Context injection is route-specific, bounded, freshness-aware, deduplicated by stable evidence identity, and observable. Reinjecting unchanged evidence is avoided when host lifecycle safely supports a per-session fingerprint; otherwise the limitation is explicit.

## Constraints

No hidden prompt mutation, no mandatory LLM/embedding call, no cross-session global mutable “last evidence,” and no weakening of DATA-only escaping.

## Required Changes

1. Bind context selection to WP-05 context retrieval and WP-04 freshness state.
2. Define stable evidence fingerprints and duplicate suppression rules.
3. Decide whether request/session-local repeat suppression is supported; `Needs verification` against Hermes lifecycle.
4. Record estimated/actual serialized token size and truncation reasons.
5. Add no-memory and memory-enabled comparative benchmarks.

## Recommended Direction

Keep current 5/3/8 evidence bounds unless measurement justifies change. Add deterministic fingerprints and optional session-local suppression owned by the adapter/client, never a process-global cache.

## Alternatives Considered

- LLM summarization on every retrieval: rejected for cost/determinism.
- Larger fixed context windows: rejected without quality evidence.
- Global repeated-evidence cache: rejected due to isolation/lifecycle risk.

## Risks

Suppressing unchanged evidence can omit needed reminders; token estimators can diverge from provider tokenization; route lexicons may miss non-English intent.

## Compatibility Impact

Envelope schema or reason-code changes require API/version migration. Hosts not supporting session state must retain safe current behavior.

## Performance Impact

Expected lower serialized context and repeated work; fingerprinting adds bounded hashing.

## Migration Impact

No persistent data migration expected. Envelope/API version changes go through WP-17.

## Tests Required

### Existing Tests

M7 router, evidence budget, hardening, injection, end-to-end; M8 integration/calibration.

### Missing Tests

Repeated-turn unchanged evidence, stale-derived state, token accounting, multilingual route behavior (`Needs verification`), and session isolation.

### Regression Tests

Evidence bounds never increase from injected text; suppressed evidence from session A cannot affect session B.

## Benchmarks Required

Context bytes/tokens, selection latency, duplicate rate, and useful-evidence hit rate across no-memory, session, project, research, and global routes.

## Acceptance Criteria

- Serialized context stays within approved evidence and token budgets.
- Context construction cost is proportional to bounded candidates, not all history.
- Freshness/insufficient states are explicit.
- Repeat suppression, if enabled, is deterministic and session-isolated.
- Token/cost claims include measured baselines and methodology.
- Default evidence begins from 5 primary, at most 3 supporting, and 3,000–6,000 tokens; any change requires benchmark-backed approval and never raises a caller above profile/server policy.
- Conflict, insufficient, freshness, omitted count, provenance, verification, and status survive serialization through every adapter/transport.

## Security / Privacy, Observability, and Rollback

Context assembly rechecks scope/sensitivity and treats evidence as data, not instruction. Metrics expose route, selected/omitted units, estimated/actual tokens, freshness, conflict/insufficiency, and truncation reason without content. Budget/fingerprint policy versions are reversible; rollback disables new suppression/ranking while preserving bounded canonical behavior.
